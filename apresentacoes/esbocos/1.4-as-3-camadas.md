# 1.4: As 3 camadas
**Fase 1: PREPARAR (mapear contexto)**

## Esqueleto (o que falar)
- Gancho: "Você já conversou com todo mundo e tem um monte de anotação. Agora vem a pergunta que trava líder novo: 'ok... e eu olho pra onde primeiro?'"
- O problema: sem um modelo, você olha para onde é confortável, e dev virando líder sempre acha confortável olhar só para o código. É a auto-sabotagem clássica: se esconder na camada que você domina.
- Apresentar o framework: todo contexto de um time cabe em **3 camadas: Clientes, Processos, Código**, nessa ordem de importância, que é exatamente a ordem inversa do seu instinto.
- **Camada 1: Clientes** (por que o time existe):
  - Quem usa o que vocês constroem? Interno, externo, os dois?
  - Como o sucesso é medido? Receita, retenção, NPS, tickets de suporte, SLA?
  - Quais são as 3 maiores dores do cliente hoje? Se ninguém no time souber responder, isso já é o achado nº 1.
  - Onde olhar: dashboards de produto, tickets de suporte, sentar com CS/vendas, usar o próprio produto por 1 hora.
- **Camada 2: Processos** (como o trabalho flui):
  - Como o trabalho entra, é priorizado, é feito e sai? (você já desenhou isso no 1.3)
  - Métricas de fluxo: lead time, frequência de deploy, taxa de retrabalho, quanto do sprint é planejado vs interrupção.
  - Cerimônias: quais existem, quais geram decisão e quais são teatro.
  - Onde olhar: board das últimas 8 semanas, histórico de sprints, quanto tempo um PR espera por review.
- **Camada 3: Código** (com o que o trabalho é feito):
  - Saúde real: cobertura onde importa, pipeline de CI/CD, tempo de build, frequência de incidentes e rollbacks.
  - Bus factor: quais sistemas só uma pessoa sabe mexer (cruze com o mapa de riscos do 1.2).
  - Dívida técnica: qual dívida de fato freia entrega vs qual só incomoda esteticamente o sênior que existe em você.
  - Onde olhar: git log (arquivos mais alterados = zonas quentes), postmortems, o setup de dev de um recém-chegado.
- A regra de leitura: problema na camada de baixo quase sempre é sintoma da de cima. Código ruim em área de mudança constante → processo de priorização ruim → cliente mal compreendido. Diagnostique de cima para baixo.
- Exemplo condutor: "time lento". O instinto diz refatorar (código), mas o mapa mostra 40% do sprint em interrupção de suporte (processo) causada por uma feature confusa (cliente). A correção certa está duas camadas acima do instinto.
- Ação prática: preencha o canvas das 3 camadas. Para cada camada, responda: o que sei, o que não sei, onde vou descobrir. Máximo 1 página por camada.
- Fechamento: "Com as 3 camadas preenchidas, você para de opinar por instinto e passa a apontar com o mapa. Falta uma direção: pra cima. É o próximo vídeo."


## O que mostrar (complementos visuais)
- Diagrama das 3 camadas empilhadas (Clientes em cima, Processos no meio, Código na base) com setas de causa descendo.
- Canvas imprimível: 3 colunas (camada) × 3 linhas (o que sei / o que não sei / onde descobrir).
- Checklist "onde olhar" por camada: fontes concretas (dashboards, board, git log, postmortems).
- Walkthrough do exemplo "time lento": o sintoma no código rastreado até a causa na camada de clientes.
- Comando/print de git log mostrando zonas quentes do repositório (arquivos mais alterados).
- Card da regra: "Diagnostique de cima para baixo, conserte de baixo para cima."
