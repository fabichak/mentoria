# 2.23: Decisões de arquitetura
**Fase 2: AGIR (Processos)**

## Esqueleto (o que falar)
- Gancho: "Por que esse sistema usa essa fila? 'Não sei, foi o cara que saiu que decidiu.' Se seu time responde isso, vocês não têm arquitetura. Têm arqueologia."
- O problema: decisões de arquitetura sem registro viram lenda oral. Cada dev novo re-questiona tudo, decisões são revertidas por ignorância, e o líder vira o único 'guardião da memória' (gargalo e risco).
- Segundo problema: o líder novo trata toda decisão com o mesmo peso: semanas debatendo nome de tabela, e escolhe o banco de dados numa tarde.
- Ideia central 1, a régua de Bezos: decisão reversível vs irreversível:
  - **Reversível (porta de duas vias)**: dá pra voltar atrás barato, então decida rápido, delegue, erre pequeno. Ex: biblioteca de UI, estrutura de pastas
  - **Irreversível (porta de uma via)**: caro ou impossível voltar, então desacelere, envolva mais gente, prototipe. Ex: banco de dados, linguagem principal, contrato de API pública, multi-tenant vs single-tenant
  - Erro nº 1 de líder: tratar tudo como irreversível (paralisia) ou tudo como reversível (desastre)
- Pergunta-teste: "quanto custa desfazer daqui a 1 ano?" Se a resposta é 'um refactor', decide o time; se é 'uma reescrita', decide com processo.
- Ideia central 2, ADR (Architecture Decision Record): a memória escrita das decisões irreversíveis (e das reversíveis importantes).
- Anatomia do ADR (1 página, 5 blocos): Contexto (que problema e restrições) → Opções consideradas (com prós/contras honestos) → Decisão → Consequências (o que aceitamos de ruim) → Status (proposto/aceito/substituído).
- O bloco mais importante é Consequências: toda decisão de arquitetura compra um problema. ADR honesto diz qual.
- Como conduzir o processo sem virar comitê: autor escreve o ADR ANTES da reunião, reunião de 30 min discute por escrito, decisão com prazo: "quem discorda, discorda no documento até sexta".
- ADR muda a dinâmica do time: discussão sai do "eu acho" pra opções comparadas; dev novo lê o histórico e entende os porquês em 1 dia; e quando o contexto mudar, você substitui o ADR em vez de reabrir guerra antiga.
- Ganho de carreira: ADRs assinados por você são portfólio de decisão, a evidência concreta de que você opera como líder técnico, não só executor.
- Armadilha: burocratizar. ADR pra tudo mata a prática. Regra: escreve ADR o que for caro de desfazer ou polêmico de lembrar.
- Ação prática: escrever seu primeiro ADR esta semana, pode ser retroativo, documentando a decisão mais questionada do sistema atual, e criar a pasta /docs/adr no repositório.
- Fechamento: "Arquitetura não é o desenho das caixinhas. É o registro dos porquês. Sistema sem ADR envelhece como fofoca: cada um conta uma versão."

## O que mostrar (complementos visuais)
- Diagrama porta de uma via vs duas vias, com exemplos técnicos em cada lado
- Template de ADR de 1 página (os 5 blocos)
- ADR real preenchido (ex: escolha de fila SQS vs Kafka) com bloco de consequências destacado
- Fluxograma do processo: escrever → revisar assíncrono → reunião 30 min → decidir com prazo
- Print de uma pasta /docs/adr com histórico numerado (a 'linha do tempo' das decisões)
