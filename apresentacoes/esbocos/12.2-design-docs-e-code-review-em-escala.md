# 12.2: Design Docs e Code Review em Escala
**Módulo 12: Side Track Técnico**

## Esqueleto (o que falar)
- Gancho: "por que fizemos assim?" Se a resposta na sua empresa é "pergunta pro Fulano, que já saiu", vocês pagam o imposto da falta de design docs todos os dias.
- Design doc não é burocracia, é a forma mais barata de errar: errar num documento custa uma tarde; errar em produção custa um trimestre.
- O que é um design doc na prática: um texto curto que responde qual o problema, quais as opções, o que foi decidido, por quê, e o que se aceita perder.
- RFC (Request for Comments): o formato mais usado. A força não está no documento, está no processo: alguém propõe por escrito, o time comenta de forma assíncrona, a decisão fica registrada. Isso dá três coisas: decisão auditável, participação de quem não fala em reunião mas comenta bem por escrito, e onboarding grátis pros próximos.
- C4 Model: o padrão pra desenhar arquitetura sem virar bagunça. Quatro níveis de zoom: Contexto, Containers, Componentes, Código. Na prática, Contexto (quem usa, com o que integra) e Containers (quais peças rodam) resolvem 90% das conversas, inclusive com quem não é técnico. Todo sistema crítico merece pelo menos um diagrama de contexto e um de containers atualizados.
- ADR (Architecture Decision Record): o primo pequeno do RFC. Meia página por decisão: contexto, decisão, consequências. Bom ponto de partida quando o time resiste a documento longo.
- Como instaurar essa cultura num time, na prática:
  - Comece pequeno: exija design doc só pra mudanças que cruzam times ou são caras de reverter. Doc pra tudo mata a cultura antes de nascer.
  - Escreva o primeiro RFC você mesmo. Cultura técnica se instala por imitação, não por decreto.
  - Crie o template e o lugar certo (repositório, wiki): atrito zero pra escrever.
  - Celebre publicamente docs que evitaram problema. O que é reconhecido se repete.
  - Combine um prazo de revisão (3 dias úteis, por exemplo): RFC sem prazo vira documento morto esperando aprovação eterna.
- Anti-padrões pra vetar: doc escrito depois da implementação (teatro), doc de 30 páginas que ninguém lê, doc sem seção de alternativas descartadas (se não teve alternativa, não teve decisão de verdade).
- Ação prática: esta semana, escolha uma decisão técnica sendo discutida no corredor ou no Slack e proponha: "escreve meia página sobre isso antes da gente decidir". Use o template de ADR. É o primeiro tijolo da cultura.
- Transição: um bom design doc evita que a arquitetura vire arqueologia; um bom code review evita que o código vire isso.
- Gancho: PR parado 4 dias esperando review, aprovado com "LGTM" em 30 segundos sem ninguém ler. Os dois extremos existem no mesmo time e nenhum dos dois é sobre ferramenta, é sobre processo mal combinado.
- Code review não é só sobre achar bug (bug se pega mais com teste do que com olho humano). É a ferramenta de cultura mais barata que existe: é onde o time ensina, aprende, alinha padrão e demonstra respeito, todos os dias, por escrito, com histórico.
- Em ordem de valor real, code review entrega: disseminação de conhecimento > alinhamento de padrões > mentoria implícita > detecção de bug.
- Os números que valem a pena auditar (em vez de ler comentário por comentário):
  - Tempo até a primeira revisão: a métrica que mais importa, PR parado é trabalho parado.
  - Tamanho médio dos PRs: PR de 1000 linhas não é revisado, é abençoado.
  - Concentração de revisores: todo mundo revisa, ou só duas pessoas? Reviewer único é gargalo e ponto único de falha.
  - Taxa de "aprovado sem comentário": muito alta, o review virou teatro.
- Padrões que valem a pena combinar com o time:
  - PR pequeno por norma (ex: limite de ~400 linhas). Acima disso, quebra em partes.
  - Prazo de review combinado: primeira resposta em X horas úteis. Review é trabalho, entra no planejamento, não é favor.
  - Autor prepara o PR: descrição do porquê, self-review antes de pedir revisão. É respeito com o tempo de quem revisa.
  - Automatize o que máquina faz melhor: lint, formatação, cobertura. Discussão humana sobre vírgula é desperdício.
- Tom dos comentários é cultura pura: comente o código, não a pessoa ("esse método", não "você"); pergunte antes de ordenar ("qual foi a intenção aqui?"); elogie quando for o caso. As pessoas copiam o tom de quem revisa com mais frequência, não o discurso.
- Sinal de alerta: alguém que destrói juniores no review, ou uma dupla que só se aprova mutuamente. Os dois casos pedem conversa individual, rápido.
- Discussão infinita no PR (15 comentários de ida e volta): regra dos 3, depois de 3 trocas sem convergir, vira uma chamada de 10 minutos. PR não é fórum de debate.
- Em escala, com vários times: guia de estilo por linguagem decidido uma vez e automatizado, critério explícito de "o que bloqueia PR vs o que é sugestão" (nit vs blocker), rodízio de revisores pra espalhar conhecimento.
- E os seus próprios PRs? Quem não aceita review no próprio código ensina que hierarquia vence qualidade. Seu PR passa pelo mesmo processo que o de todo mundo.
- Ação prática: puxe os últimos 20 PRs do time e responda: tempo médio até primeira review, tamanho médio, quem revisou. 30 minutos de análise que dão um diagnóstico completo de cultura. Escolha um padrão pra instaurar este mês (sugestão: prazo de primeira resposta).
- Fechamento: mostra os code reviews de um time e eu te digo a cultura de engenharia dele. É o artefato mais honesto que existe, e quem entende de auditar o processo (não cada PR individualmente) escala qualidade sem virar gargalo.

## O que mostrar (complementos visuais)
- Template de RFC de 1-2 páginas (problema, alternativas, decisão, consequências, aberto para comentários até DD/MM)
- Template de ADR de meia página
- C4 desenhado ao vivo: níveis 1 e 2 de um sistema exemplo, mostrando que 2 diagramas bastam
- Linha do tempo: como uma decisão sem doc vira "arqueologia de código" 18 meses depois (exemplo real)
- Checklist de implantação da cultura: template → primeiro doc → critério de quando exigir → prazo de revisão → celebração
- Dashboard exemplo: tempo até 1ª review, tamanho de PR, distribuição de revisores (dá pra montar com dados reais do GitHub/GitLab)
- Antes/depois de comentário de review: tom agressivo vs tom de mentoria, mesmo conteúdo técnico
- A "regra dos 3": fluxo comentário → comentário → comentário → call de 10 min
- Tabela nit vs blocker: o que trava PR e o que é sugestão
- Checklist de PR bem preparado (descrição, contexto, self-review, tamanho)
- Exemplo real: gráfico de lead time caindo depois de instaurar prazo de review
